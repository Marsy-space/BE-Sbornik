# ADR-0002: Модульный монолит

| Параметр | Значение |
| -------- | -------- |
| Статус | Принято |
| Дата | 15.11.2026 |
| Участники обсуждения | Морозова К., Стахейко П., Борозна Д., Шугар В. |

## Контекст
Проект разрабатывается командой из 4 человек за 8 спринтов. Основные требования: высокая скорость разработки, простота развертывания (одна команда `docker compose up`), возможность быстрого внесения изменений. 

## Рассмотренные варианты
1. **Слоистый монолит**: вся логика разбита на слои (контроллеры, сервисы, репозитории). Минус: сложно контролировать связанность между разными бизнес-функциями.
2. **Модульный монолит**: код разбит на модули по бизнес-функциям (auth, recipes, favorites, chat). Каждый модуль изолирован.
3. **Микросервисы**: каждый модуль — отдельный сервис. Минус: огромные накладные расходы на сеть, развертывание и отладку для команды из 4 человек.

## Решение
Выбран **Модульный монолит**. Это дает нам четкую структуру кода (как в микросервисах), но сохраняет простоту развертывания и отладки единого приложения (как в монолите).

## Последствия
**Положительные:** проще тестировать, один Docker-контейнер для бэкенда.
**Отрицательные и риски:** нужно строго следить за тем, чтобы модули не обращались к внутренностям друг друга напрямую (только через публичные интерфейсы).
